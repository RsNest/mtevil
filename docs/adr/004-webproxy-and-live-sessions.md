# ADR-004: Интеграция Telegram WEB Proxy (`tproxy-server` sidecar), живой `cover` и мягкое завершение сессий

- **Статус:** accepted (реализовано в `v0.3.3`)
- **Дата:** 2026-11-26
- **Уточняет:** [ADR-000](000-architecture-baseline.md) (§2, §4 INV-01 / INV-07 / INV-10), [ADR-003](003-masking-improvements.md)

---

## 1. Контекст и верификация фактов по протоколу

Полевые проверки `v0.3.1`–`v0.3.2` на жёстких сетях показали чёткую границу возможностей FakeTLS (`ee`):
- Реальный HTTPS-запрос (`TLS 1.3` + `HTTP/2`) к тому же узлу проходит штатно (`HTTP 200`, валидный сертификат), тогда как двухсегментный FakeTLS `ClientHello` штатного мобильного клиента (`1532–1553` байт) может терять хвост после первого сегмента `1448` байт (`client_hello_incomplete`) либо зависать после 3-записного `ServerHello` (`inner_header_incomplete`).
- Одновременно при ревизии проекта проверены четыре распространённых заблуждения о протоколе `ee` в `mtevil`, чтобы не вносить разрушающие совместимость правки:
  1. **`ServerHello.random` в FakeTLS не нулевой:** смещение `flight[11..43]` в `crates/proto/src/wire.rs` перезаписывается 32-байтным `HMAC-SHA256(secret, client_random || zeroed_flight)`. Замена этого поля на `unixtime + entropy` сломает проверку подлинности у 100% клиентов Telegram.
  2. **В steady-state у `ee` есть TLS-record framing (`0x17 0x03 0x03 <len>`):** его читает `TlsReader` и формирует `download(..., framed = true)`.
  3. **Современные клиенты Telegram не шлют «2 шифра и 3 расширения»:** минимальный шаблон в `wire::build_client_hello` относится только к синтетическому тестовому генератору (`probe-telegram` / `harness`); реальные клиенты присылают расширенный `ClientHello` (~`1.5` КБ) с GREASE и ALPN.
  4. **Расширение `server_name` (`0x0000`) запрещено в открытом TLS 1.3 `ServerHello` по RFC 8446 §4.1.3 / §4.2:** в настоящем TLS 1.3 оно передаётся внутри зашифрованного `EncryptedExtensions`, а в открытом `ServerHello` присутствуют только `key_share` (`51`) и `supported_versions` (`43`).

## 2. Архитектурные решения `v0.3.3`

### 2.1 WEB Proxy как sidecar `telegramdesktop/tproxy-server` перед `mtevil` (`dd`)

Вместо дублирования молодого HTTP/WebSocket/JS-моста внутри Rust-ядра `mtevil` в `v0.3.3` принята композиционная схема на базе эталонного `telegramdesktop/tproxy-server` (зафиксированный коммит и `SHA-256` архива исходников):

```text
Telegram (WebView, настоящий TLS 1.3 / HTTP/2 / WSS)
  │
  ▼ :443
Caddy / nginx (внешняя TLS-терминация, валидный сертификат, без логирования URI)
  │  loopback HTTP / WebSocket
  ▼ 127.0.0.1:8080
tproxy-server (sidecar-контейнер, UID 10001:10001, read-only rootfs, cap_drop: ALL)
  ├── неаутентифицированные запросы ──▶ публичный сайт (./site или локальный HTTP upstream)
  └── валидный bridge/session ────────▶ 127.0.0.1:2398  mtevil (enable_dd = true)
                                                          │
                                                          ▼
                                       Direct / каскад edge→egress (MTV3/MTV4) / ME-pool
```

**Почему выбран sidecar, а не переписывание в ядре на текущем этапе:**
- `mtevil` уже нативно принимает чистый `obfuscated2` (`enable_dd = true`: `abridged`, `intermediate`, `padded-intermediate`) с защитой от повторов (`guard`), маршрутизацией `edge → egress` (`MTV3`/`MTV4`), хеджированием и пулом `ME`.
- Использование апстримового `tproxy-server` сохраняет побайтовую совместимость JS-страницы-моста, CSP и протокола фреймов с клиентами Telegram по мере их обновления, не раздувая поверхность безопасности бинаря `mtevil`.
- Секретные файлы `tproxy-token.key` (ровно 32 случайных байта, `0600`) и `tproxy-profiles.json` (`0600`, синхронизируется с `proxy-secret` и `users.json`) хранятся внутри Docker-тома `state` под `10001:10001` и не попадают в открытом виде в каталог хоста.
- Классический режим `tg://proxy` (`ee`/`dd`) полностью сохраняется как основной для установок без домена и клиентов без поддержки `tg://webproxy`.

### 2.2 Живое поведение `cover` при активном зондировании

В `crates/data-plane/src/cover.rs` устранены три неестественных признака при обращении браузера или зонда:
1. **Ожидание в очереди `cover_permits` вместо мгновенного закрытия за `0 мс`:** при исчерпании лимита `cover_permits` соединение ожидает освобождения слота в пределах короткого окна с джиттером (`80..=200 мс`, не более `handshake / 4`), и при отказе закрывается штатным `FIN` (`SHUT_WR` + короткий дренаж чтения), не порождая `RST`.
2. **Плавное закрытие при недоступности `cover`:** мгновенный отказ соединения (`ECONNREFUSED` / пустой кэш DNS быстрее `50 мс`) сглаживается коротким джиттером перед `FIN`.
3. **Сохранение HTTP keep-alive после первого ответа сайта:** жёсткий общий бюджет `2 * handshake` теперь ограничивает только получение **первого ответа** от `cover` (`plain_copy_first_then_idle`), защищая от молчащих соединений; после первых байтов `ServerHello` соединение живёт по `cover_idle` (до `60 с`), не обрывая открытую в браузере страницу через 20 секунд.

### 2.3 Кооперативный `drain` и живое закрытие сессий (`FIN` вместо `RST`)

В `crates/data-plane/src/serve.rs`, `relay.rs` и `me.rs`:
- Цикл `serve()` при остановке рассылает сигнал `drain` всем активным соединениям (`Direct`, `edge → egress`, `ME`, `cover` и незавершённым pre-commit сокетам).
- Активные сессии корректно закрывают запись (`SHUT_WR` → `TCP FIN`) и дренируют входной буфер (`graceful_fin_close`), избегая генерации ядром `TCP RST` из-за непрочитанных байтов в `SO_RCVBUF`. То же применяется при истечении `idle_timeout`.
- Жёсткий `tasks.abort_all()` и счётчик `mtevil_forced_close_total` сохраняются строго как крайний страховочный механизм по истечении `drain_timeout_secs` (`INV-10` / `F-29`).

### 2.4 Гигиена тестов и репозитория

- Убрано сочетание `#[tokio::test(start_paused = true)]` с реальными TCP-сокетами ядра ОС во всём воркспейсе (`crates/data-plane/src/tests.rs` и `crates/me-pool/src/lib.rs`), устраняющее гонку виртуальных часов Tokio против планировщика ОС под нагрузкой CI.
- В корень репозитория добавлены тексты лицензий `LICENSE-MIT` и `LICENSE-APACHE` в соответствии с `Cargo.toml` (`MIT OR Apache-2.0`).
- В `crates/proto/src/wire.rs` статический пул `KEY_SHARE_POOL` в синтетическом генераторе `build_client_hello` заменён на генерацию свежей эфемерной пары `X25519`.
- В `.github/announce_release.py` регулярное выражение `RELEASE_TAG` расширено на все корректные SemVer pre-release теги (`alpha`, `beta`, `rc`).
