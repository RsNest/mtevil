# ADR-003: Улучшения маскировки FakeTLS (`mtevil`) по итогам аудита v0.3.0

- **Статус:** proposed (только предложения, без изменения продуктового кода)
- **Дата:** 2026-11-23
- **Основание:** [docs/dpi-audit/REPORT.md](../dpi-audit/REPORT.md)

---

## 1. Контекст

Аудит маскировки `mtevil v0.3.0` выявил ряд конкретных пассивных и активных отличий от реальных TLS 1.3 серверов, часть которых устраняется только настройкой/выбором SNI, а часть — точечными доработками в `crates/proto` и `crates/data-plane`.

Важное ограничение совместимости: штатный клиент Telegram (`TelegramMessenger/mtproto-engine`, `verify_server_hello`) строго читает **ровно 3 TLS-записи** (`ServerHello` `0x16`, `ChangeCipherSpec` `0x14`, 1 запись `ApplicationData` `0x17`) до отправки клиентского `obfuscated2` init и считает `HMAC-SHA256` по всему 3-записному флайту. Любые изменения до клиентского ответа обязаны сохранять 3-записную структуру.

---

## 2. Что решается без изменения кода (настройка и выбор SNI)

1. **Отказ от `example.com` как SNI по умолчанию:**
   - В документации и мастере установки рекомендовать домены без монопольной CDN-AS (или собственный домен на том же VPS/соседней машине), соответствующие региону VPS.
2. **Включение разброса размера «сертификата» (`fake_tls_cert_jitter`):**
   - Использование `fake_tls_cert_bytes` ближе к размеру флайта реального `cover` (например, `3700..4800` байт для BoringSSL-подобных серверов в пределах лимита `10 KiB`) и `fake_tls_cert_jitter` (`128..256` Б) убирает жёсткую константу `3016` Б на проводе.

---

## 3. Предлагаемые изменения в коде (для будущих версий)

### 3.1. Исправление `CoverResolver` и IPv6 в Docker `bridge` (Приоритет 1, Высокая серьёзность)
- **Проблема:** `tokio::net::lookup_host` возвращает `AAAA`-записи (например, у `example.com`, `google.com`, `ya.ru`), `CoverResolver` пробует их по `round-robin`, и в Docker `bridge` без IPv6 ~50% активных проб падают с `ENETUNREACH (os error 101)` → мгновенный `FIN` (`0` Б).
- **Предложение:** при ошибке `TcpStream::connect` с `ENETUNREACH`/`EADDRNOTAVAIL` (или при проверке доступности IPv6 на старте) фильтровать неподдерживаемое семейство адресов либо перебирать оставшиеся адреса из кэша `CoverResolver` до возврата ошибки.
- **Трудоёмкость:** ~30 LOC в `crates/data-plane/src/cover.rs`.

### 3.2. Настраиваемый порядок расширений `ServerHello` (`51-43` vs `43-51`) и приоритет шифра (Приоритет 2, Средняя серьёзность)
- **Проблема:** `mtevil` всегда отдаёт расширения `[43, 51]` (`supported_versions`, `key_share`) при 3 записях, хотя проверенные 3-записные серверы (Cloudflare, Google, Yandex) используют `[51, 43]`, а `[43, 51]` характерен для 6-записных OpenSSL/Nginx серверов. Также `mtevil` слепо берёт первый TLS 1.3 шифр клиента вместо серверного приоритета.
- **Предложение:** добавить в `ServerFlightProfile` поле порядка расширений (`ExtensionOrder::KeyShareFirst` `51-43` для 3-записных профилей и `SupportedVersionsFirst` `43-51`) + возможность задавать приоритетный шифр (или автоподстройку при старте по единичному probe к `cover`).
- **Совместимость:** клиент Telegram парсит расширения по типу, порядок `51-43` полностью совместим с RFC 8446 и `verify_server_hello`.
- **Трудоёмкость:** ~40 LOC в `crates/proto/src/wire.rs` + `config.rs`.

### 3.3. Устранение коллизий `KEY_SHARE_POOL` (Приоритет 3, Низкая/Средняя серьёзность)
- **Проблема:** пул из 64 ключей даёт заметные повторы уже на 20–200 соединениях.
- **Предложение:** генерировать свежий эфемерный X25519-ключ на каждый handshake (используя `x25519-dalek`, MIT/Apache-2.0, либо расширенный пул).
- **Трудоёмкость:** ~20 LOC.

### 3.4. Эмуляция `NewSessionTicket` после клиентского `obfuscated2` init (Приоритет 4, Исследовательский)
- **Проблема:** 6 из 6 реальных доменов отправляют 2 записи `NewSessionTicket` сразу после клиентского `Finished`, `mtevil` — 0.
- **Ограничение:** если отправить `NewSessionTicket` до чтения ответа DC, он не должен сломать расшифровку `obfuscated2` у клиента Telegram (клиент ждёт 0x17-записи с зашифрованным `obfuscated2`-потоком от DC). Поэтому отправка фиктивных тикетов **небезопасна без проверки исходного кода и живых клиентов iOS/Android/Desktop**: если клиент трактует каждую `0x17`-запись после `ServerHello` строго как MTProto-поток, лишний `0x17` сломает AES-CTR синхронизацию.
- **Решение:** оставить только как исследовательскую задачу с обязательной проверкой на всех штатных клиентах.

### 3.5. Включение `flight_shaping` / авто-профиля `cover`
- Опциональное снятие профиля `cover` при старте (`JA3S`, порядок расширений, суммарный размер флайта) для автоматического выставления `fake_tls_cert_bytes`, `jitter` и порядка расширений под выбранный `sni`.
