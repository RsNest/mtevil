# Профиль ServerHello-полёта FakeTLS

Документ закрывает висячее требование ADR-000 §5.2: «SH-полёт: одна
AppData-запись «сертификата» (ограничение клиента), размер из профиля
(§11C)». ADR-000 неизменяем, поэтому профиль зафиксирован здесь, а §5.2
ссылается на §11C как на раздел этого документа.

## 1. Что определяет профиль

Полёт FakeTLS состоит ровно из трёх TLS-записей. Такую структуру читает
штатный клиент Telegram:

`TelegramMessenger/mtproto-engine`, `crates/mtproto-core/src/transport/tls.rs`,
функция `verify_server_hello`:

```text
запись 1: 16 03 03 | u16 len | 122 B  ServerHello
запись 2: 14 03 03 00 01 01                       ChangeCipherSpec
запись 3: 17 03 03 | u16 len | len B  «сертификат» (ApplicationData)
```

Клиент читает **все три записи целиком**, прежде чем отвечать, и считает
HMAC-SHA256 по всему буферу (с обнулённым слотом random `[11:43]`), добавив
к байтам клиентский random. Прокси задаёт размер полёта, а клиент читает
длину каждой записи из её заголовка.

Клиент ждёт недостающие байты, если полёт доставлен частично. В прогонах на
МГТС зафиксировано отсутствие полного ответа клиента. Доставку серверного
полёта до приложения журнал пересылки не измеряет.

## 2. Размер «сертификата»

Размер AppData-записи — единственный свободный параметр полёта. Источники:

| Источник | Значение |
|---|---|
| `TelegramMessenger/mtproto-engine`, `transport/tls.rs` | `MAX_TLS_PACKET_LENGTH = 2878` — предел собственной TLS-записи клиента |
| `mtg` v2, `mtglib/internal/tls/fake/server_side.go` | 2500..4700 B (legacy) либо `Mean ± Jitter` с полом 1000 — «combined size of a real TLS 1.3 encrypted server handshake» |
| `mtdd` (упоминается в реестре свидетельств) | `kFakeCertSize = 2878` |
| `telemt` @ `dac7aee`, `docs/Architecture/Fronting-splitting/TLS_FRONT_PROFILE_FIDELITY.ru.md` | размеры AppData-записей берутся из захваченного профиля origin-сервера (`app_data_record_sizes`, `ticket_record_sizes`) |

**Принятое значение тестового профиля: 2878 байт.** Оно попадает в диапазон
эталонной реализации и совпадает со значением `kFakeCertSize`. Размер
исходящих записей клиента и предел приёма ServerHello — разные параметры.

Историческая (до 2026-11-18) сборка выбирала 512..1023 B случайно — это и
было невыполнение §5.2. Замер origin-сервера в том же прогоне: ответ
cover-пути на `example.com` составил 7425 B, то есть реальный полёт в
6..11 раз длиннее прежнего.

## 3. Настройка

```json
{
  "fake_tls_cert_bytes": 2878,
  "fake_tls_cert_jitter": 0
}
```

- `fake_tls_cert_bytes` — размер AppData-записи, 512–10240. Верхняя
  граница соответствует проверке длины в Telegram iOS.
- `fake_tls_cert_jitter` — симметричный разброс, 0..1024 и меньше размера.

Полёт целиком равен `138 + fake_tls_cert_bytes` байт.

**Сравнение размеров.** Клиент проверяет полёт целиком. При `2878` полёт занимает 3016 B и
разбивается на 3 сегмента при MSS 1448; при прежних 512..1023 B он умещался в
один сегмент. Если downlink на канале нестабилен, разумно выставить
`fake_tls_cert_bytes: 512` и вернуть односегментный полёт. Выбор между
фидельностью профилю и устойчивостью доставки — эксплуатационный, а не
протокольный.

## 4. Прочие параметры полёта

| Параметр | Значение | Источник |
|---|---|---|
| Шифронабор в ServerHello | первый предложенный поддерживаемый TLS 1.3 suite (0x1301–0x1303) | порядок предложений клиента с фильтром по версии TLS |
| Session ID | эхо клиентского | `mtg` v2, то же |
| Расширения | `supported_versions` (TLS 1.3) + `key_share` (x25519, 32 B) | `mtg` v2, `serverHelloSuffix` |
| key_share | 32 случайных байта, **не** валидная точка X25519 | известное расхождение с эталоном: `curve25519` в зависимости нет, клиент значение не проверяет |
| Границы окна времени | ±120 с | ADR-000 §5.2 |

Выбор из предложений клиента позволяет использовать 0x1302 и 0x1303.
Устаревшие наборы шифров и GREASE пропускаются.

## 5. Что профиль не решает

Профиль меняет размер ответа после аутентификации ClientHello. Сравнение
профилей не объясняет потери до этой точки.
В `inner_header_incomplete` есть размер отправленного ответа и число
байт, прочитанных после него, включая части записей. Это позволяет
различить полное молчание и частичный ответ клиента. Для подтверждения
доставки серверного ответа нужен TCP ACK или захват на клиенте.
