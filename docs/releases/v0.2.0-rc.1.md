# mtevil v0.2.0-rc.1

Кандидат стабильного production-релиза `mtevil` (`direct` и `edge → egress`). Обратная совместимость клиентского протокола (`FakeTLS` / `obfuscated2`), существующих `config.json`, ссылок `t.me/proxy` и `mtevilctl update`/`rollback` сохранена.

## Что изменено

### Отказоустойчивость процесса и ресурсов
- **Устойчивый accept-цикл (`F-15`):** ошибки `ECONNABORTED`/`ECONNRESET`/`EINTR`/`WouldBlock` обрабатываются немедленно без падения listener'а; ошибки исчерпания ресурсов (`EMFILE`/`ENFILE`/`ENOBUFS`/`ENOMEM`) используют экспоненциальный backoff (`10 мс → 1 с`) со сбросом после успеха, rate-limited событиями `accept_error` (≤1/с на вид) и счётчиками `mtevil_accept_errors_total{kind}`.
- **Бюджет файловых дескрипторов (`F-15`):** при старте читается `RLIMIT_NOFILE`, эффективный лимит соединений ограничивается `min(max_connections, (nofile - 128) / 2)` (fail-fast при `< 16`); `setup.py` автоматически выставляет `ulimits.nofile = max(4096, max_connections * 2 + 512)`.

### Failover `edge → egress`
- **Circuit breaker для всех стратегий (`F-23`):** `EgressHealth` теперь активен и для `round-robin` (мёртвые узлы пропускаются с сохранением RR-смещения).
- **Fail-open при падении всех узлов (`F-24`):** если все узлы `egress` в cooldown, выполняется принудительная проба узла с ближайшим сроком окончания cooldown (максимум 1 такая проба на узел одновременно). Время восстановления после полного падения и возврата узлов сокращено с окна 15 с до ~90 мс.
- **Экспоненциальный backoff cooldown:** конфигурируемые `egress_cooldown_base_ms` (по умолчанию `3000`) и `egress_cooldown_max_ms` (по умолчанию `60000`), рост `×2`, jitter `±20%`, сброс при успехе, раздельное отслеживание сбоев узла и конкретного DC.
- **Фоновые пробы управляют breaker:** `monitor_edge_egress` ротирует DC (`2, 4, -2, -4`), переключает период `30 с` ↔ `5 с` при деградации (`egress_probe_interval_secs`, `egress_probe_degraded_interval_secs`), ставит и снимает cooldown без жертвования живым клиентским трафиком.
- **Hedged connect (`ordered` и `round-robin`):** опция `egress_hedge_ms` (по умолчанию `400` мс, `0` — выкл), адаптивный `per_try` (`3 × медиана успешных ACK`, в пределах `300 мс..2 с`) и мгновенный сигнал «узел недоступен» для параллельных попыток к тому же узлу.
- **Single-flight для принудительной пробы:** при одновременном восстановлении после падения всех узлов параллельные соединения ждут результат единственной принудительной пробы в рамках бюджета `handshake` вместо немедленного отказа.

### Безопасность и устойчивость данных
- **Протокол `MTV3` и защита `egress` (`F-31`):** аутентификация `HMAC-SHA256(token, magic||dc||timestamp||nonce||dc_header)` в constant-time, окно времени `±30 с`, конфигурируемый replay-кэш `nonce` (`egress_nonce_cache_capacity`, при насыщении принимает с метрикой/событием `egress_nonce_cache_full`), фильтрация источников по CIDR (`egress_allow_from` с нормализацией IPv4-mapped IPv6 `::ffff:a.b.c.d`), sliding-window лимит неудачных аутентификаций на IP (`egress_max_failed_per_ip` с вытеснением самых старых записей при заполнении `egress_failed_tracker_evictions` и без штрафа за оборванные до конца префейса соединения `egress_preface_aborted`), отдельный семафор незавершённых handshake и предупреждение `egress_public_listen_warning`.
- **Изоляция томов `state` и `replay` (`F-22`):** том `state` (секреты `proxy-secret`, `users.json`, `allowed-sni.txt`, `egress-token`) смонтирован `:ro` для основного процесса `mtevil`, запись пользователей и SNI выполняется через одноразовый сервис `init` (`profiles: [tools]`) с горячей перезагрузкой `users.json` без рестарта; `replay.bin`, `runtime-stats.json` и `edge-alerts.jsonl` вынесены в отдельный rw-том `replay` (`/var/lib/mtevil-replay`, права `0700`). При загрузке `replay.bin` очередь истечения сортируется по времени; повреждённый файл переинициализируется без сбоя старта (`replay_table_reinitialized`, принятый риск ≤ 120 с).
- **Длинные загрузки через `egress` (`F-32`):** общий двунаправленный таймштамп активности в `counted_copy` — однонаправленные загрузки дольше `idle_timeout_secs` не обрываются, пока есть прогресс.
- **Конфигурируемый `dc_media_override` и фоновая самопроверка DC (`F-23`):** резервные адреса медиа-DC вынесены в конфиг, фоновая проверка `dc_self_check` раз в `60 с` (`dc_probe_interval_secs`) не меняет маршрутизацию.
- **Фоновый DNS-кэш `cover` (`F-01`, `F-02`):** `CoverResolver` с TTL `60 с` (`cover_dns_ttl_secs`) и сохранением `last-known-good` при ошибках и таймаутах DNS; data-потоки больше не блокируются на DNS.
- **Ограниченная очередь webhook-алертов (`E6`):** очередь ёмкостью `64` и `2` фиксированных воркера (метрика переполнения `mtevil_alert_webhook_dropped_total`); локальный `edge-alerts.jsonl` не зависит от очереди.

### Производительность, наблюдаемость и проверяемость
- **Снижение числа системных вызовов `TCP_INFO` (`T12`):** `getsockopt(TCP_INFO)` опрашивается раз в `1 с` на сессию и при закрытии вместо каждого чанка; покадровая трассировка `timeline.mark` вынесена за флаг `diagnostics: false`. (Замеры показывают снижение числа `getsockopt` на 92–99.9%; стабильного прироста пропускной способности на 1 vCPU в пределах разброса не зафиксировано.)
- **Prometheus `/metrics` (`T13`):** опциональный localhost-only эндпоинт (`metrics_listen`, по умолчанию выключен).
- **Тестирование и CI:** интеграционный chaos-набор (`tests/inv/chaos_egress.rs`), 4 `cargo-fuzz` таргета для `proto::wire`, GitHub Actions CI (`.github/workflows/ci.yml`), модуляризация `data-plane` и очистка workspace (`mtevil-guard`, `mtevil-egress`).

### Смешанные версии и обновление (A4)
- Новый `egress` (`egress_accept_legacy=true`) + старый `edge` (`v0.1.5`, `MTV2`): **PASS** (`rtt = 7 мс`).
- Новый `egress` + новый `edge` (`MTV3`): **PASS** (`rtt = 9 мс`).
- Новый `egress` (`egress_accept_legacy=false`) + старый `edge` (`v0.1.5`, `MTV2`): **корректный отказ** с событием `egress legacy MTV2 disabled`.
- `mtevilctl update` при сбое пробы (`v0.1.5 → v0.2.0-rc.2`): автооткат на `v0.1.5` (проба `17 мс`); чистое обновление `v0.1.5 → v0.2.0-rc.1`: **PASS** (`8 мс`); ручной `mtevilctl rollback`: **PASS** (`31 мс`).

## Порядок обновления (`edge ↔ egress`)

1. **Сначала обновите все узлы `egress`:**
   ```bash
   ./mtevilctl update --version v0.2.0-rc.1 --prerelease
   ```
   По умолчанию на `egress` включён переходный режим `egress_accept_legacy: true`, поэтому существующие `edge` (`v0.1.5`, `MTV2`) продолжают работать без перерыва.
2. **Затем обновите все узлы `edge`:**
   ```bash
   ./mtevilctl update --version v0.2.0-rc.1 --prerelease
   ```
   Новые `edge` автоматически переходят на `MTV3` (`egress_use_mtv3: true`). При сбое сквозной Telegram-пробы `mtevilctl update` автоматически откатит предыдущую версию.
3. **Для `direct`-инсталляций** достаточно выполнить `./mtevilctl update --version v0.2.0-rc.1 --prerelease` на сервере.

## Переход на строгий режим `MTV3`

1. После обновления всех `edge` проверьте статус на каждом `egress`:
   ```bash
   ./mtevilctl status
   ```
   Убедитесь, что счётчик `legacy MTV2` перестал расти (или равен `0`), а подключения идут по `MTV3` (также доступно в `/metrics`: `mtevil_egress_legacy_connections_total` и `mtevil_egress_mtv3_connections_total`).
2. В `config.json` на каждом `egress` выставьте:
   ```json
   "egress_accept_legacy": false
   ```
   и перезапустите контейнер `egress`. После этого подключения `MTV2` будут отклоняться с событием `egress legacy MTV2 disabled`.

## Известные ограничения

- **`edge` является единой точкой отказа (SPOF):** failover защищает от падения узлов `egress` и туннелей между `edge` и `egress`, но не от недоступности самого `edge`-сервера.
- **Активные сессии при падении узла `egress` рвутся:** TCP-соединение через умерший `egress` закрывается, после чего Telegram-клиент автоматически переподключается через живой `egress` (failover работает на уровне новых подключений и переподключений).
- **Область поддержки:** Linux `x86_64` и IPv4 (`direct` и `edge → egress`). Сквозной IPv6 не проверялся и не заявляется.
- **Обновление без zero-downtime:** `mtevilctl update` перезапускает контейнер; текущие сессии завершаются с `drain_timeout_secs`, затем клиенты переподключаются.
