# mtevil v0.3.0

Стабильный релиз `mtevil` с поддержкой режима Telegram Middle-End (ME), рекламного тега `@MTProxybot` (`ad_tag`) и протокола `MTV4` для разделённой схемы `edge → egress`.

**ME-режим выключен по умолчанию (`me.enabled = false`).** Существующие установки, `config.json`, ссылки `t.me/proxy` и пользователи после обновления работают в режиме Direct без изменений.

## Что нового

- **Режим Telegram Middle-End (ME) и `ad_tag` (`direct` и `edge → egress`):** собственный clean-room пул постоянных шифрованных соединений к ME-серверам Telegram (`pool_size = 2` по умолчанию), автообновление `proxy-secret` и `proxy-multi.conf` с `core.telegram.org` с сохранением `last-known-good` кэша в томе `replay`, бесшовный дренаж при смене конфигурации и поддержка всех трёх клиентских транспортов (`abridged`, `intermediate`, `padded-intermediate`).
- **Автоматический fallback на Direct:** при недоступности ME-пула и `me.fallback_to_direct = true` (по умолчанию) новые соединения прозрачно переключаются на Direct.
- **Протокол `MTV4` (`edge → egress`):** аутентифицированный (`HMAC-SHA256`, окно `±30 с`, replay-защита `nonce`) и фреймированный транспорт для ME-сессий между `edge` и `egress`. Если часть узлов `egress` ещё работает на `v0.2.0`, `edge` быстро изолирует их в отдельном cooldown `MTV4` (`30 с`) и при `fallback_to_direct = true` переходит на Direct по `MTV3` без блокировки узла.
- **Управление рекламным тегом `mtevilctl adtag`:** команды `mtevilctl adtag set`, `show` и `clear`. При запуске `mtevilctl adtag set` без аргумента тег вводится скрыто (или через `stdin`), не попадая в историю shell; файл записывается в том `state` с правами `0600`, владельцем `10001:10001` и проверкой чтения от UID `10001`, а демон подхватывает изменения без перезапуска контейнера.
- **Мастер и диагностика:** расширенный режим `mtevilctl setup` поддерживает настройку ME (`public_ipv4`, `pool_size`, `fallback_to_direct`, `send_client_ip`); `mtevilctl status` отображает состояние ME-пула и статус `ad_tag` (значение маскируется); добавлены метрики Prometheus `mtevil_me_*`.

## Как включить ME и задать `ad_tag`

1. Запустите расширенный мастер `mtevilctl setup` (или добавьте блок `"me"` в `config.json`, см. [docs/me-manual-test.md](../me-manual-test.md)).
2. За 1:1 NAT или в Docker `bridge`-сети обязательно укажите внешний IPv4 сервера в `me.public_ipv4`.
3. Задайте рекламный тег из `@MTProxybot` (32 hex-символа) без сохранения в истории shell:
   ```bash
   mtevilctl adtag set
   ```
4. Проверьте состояние пула и статус тега:
   ```bash
   mtevilctl status
   ```

## Обновление, проверка и откат

При обновлении контейнер перезапускается с graceful drain (`drain_timeout_secs`, по умолчанию `5 с`): активные сессии кратковременно прерываются, после чего клиент Telegram автоматически переподключается по той же ссылке.

- **Обновление (канал `stable` по умолчанию):**
  ```bash
  mtevilctl update
  ```
- **Проверка статуса и версии:**
  ```bash
  mtevilctl status
  ```
- **Откат на предыдущую версию (`v0.2.0`):**
  ```bash
  mtevilctl rollback
  ```
- **Понижение версии при включённом ME (`mtevilctl update --version v0.2.0` или `mtevilctl rollback`):** блок `"me"` автоматически вырезается из `config.json` для совместимости с `v0.2.0`, а исходный конфиг сохраняется в `config.json.pre-me-downgrade` (`0600`).

## Порядок обновления для разделённой схемы (`edge → egress`)

1. **Сначала обновите все серверы `egress`** (резервный → основной): выполните `mtevilctl update` на каждом `egress`. Существующие `edge v0.2.0` продолжат работать без потери совместимости.
2. **Затем обновите серверы `edge`:** выполните `mtevilctl update` на каждом `edge`.
3. Если планируете включать ME в split-схеме, включите его на всех узлах `egress`, а затем на `edge`.

## Приватность в ME-режиме

- В режиме Direct Telegram видит только IP-адрес вашего прокси-сервера.
- В режиме ME при значении по умолчанию `me.send_client_ip = true` в Telegram передаётся **реальный IPv4-адрес клиента** (как в официальном MTProxy; при включённом `proxy_protocol` — из PROXY protocol v2; для чистых IPv6-клиентов передаётся `0.0.0.0:0`).
- В схеме `edge → egress` передача IP клиента активна только при `me.send_client_ip = true` на обоих узлах (AND-логика); клиентские IP и `ad_tag` никогда не пишутся в логи и метрики.
- Вариант `me.send_client_ip = false` (`0.0.0.0:0`) помечен как экспериментальный до проверки полной сессии реальным клиентом Telegram.

## Известные ограничения

- **`edge` — единая точка отказа (SPOF):** failover защищает от падения узлов `egress`, но не от недоступности самого `edge`.
- **Область поддержки:** Linux `x86_64` и IPv4 (`direct` и `edge → egress`). Сквозной IPv6 не проверялся и не заявляется.
- **Проверенная нагрузка и ограничения ME:** режим ME и `MTV4` проверены на изолированном Linux-стенде (волны до 100 параллельных сессий, пробы `req_pq_multi → resPQ` с реальным `ad_tag` в `direct` и `split MTV4` по всем 3 транспортам, совместимость с `v0.2.0`), но **не** под массовой пользовательской нагрузкой. Полная сессия реального клиента Telegram в режиме ME и отображение спонсорского канала по `ad_tag` из `@MTProxybot` проверяются только вручную — используйте [docs/me-manual-test.md](../me-manual-test.md).
