# mtevil v0.4.1

Сервисный релиз усиления безопасности, отказоустойчивости и гигиены репозитория для линейки `v0.4.x`.

### Что нового
- **Валидация `proxy_protocol` и список доверенных источников (`proxy_protocol_allow_from`):**
  - Конфигурация запрещает `proxy_protocol: true` на роли `egress`, а на `direct` и `edge` требует либо привязку `listen` к loopback (`127.0.0.1`, `::1`, `::ffff:127.0.0.1`), либо явный список доверенных подсетей в поле `proxy_protocol_allow_from` (флаг `--proxy-protocol-allow-from`).
  - На уровне data-plane подключения к сокету с `proxy_protocol: true` от недоверенных адресов отклоняются событием `proxy_protocol_untrusted_peer` **до** чтения заголовка `PROXY v2` и никогда не передаются на `cover`.
- **Гигиена логов для секретного пути `egress_ws_path`:**
  - В шаблон `nginx.egress.example` добавлено отключение `access_log off;` непосредственно внутри `location = <path>` (плюс пример маскирования `$request_uri`), а в `Caddyfile.egress.example` — директива `log_skip @mtevil_egress`.
  - В интерактивный мастер настройки (`--egress-ws`) и руководство [deploy/README.md](../../deploy/README.md) добавлены предупреждения о недопустимости записи секретного пути в журналы доступа обратного прокси.
- **Ограниченные парсеры, fuzz-таргеты и стресс-тест `ws_egress`:**
  - Парсеры HTTP/1.1 Upgrade (`8 КиБ`) и заголовков фреймов RFC 6455 (`64 КиБ`) вынесены в крейт `mtevil-proto::ws`, покрыты двумя новыми libFuzzer-таргетами (`fuzz_ws_http_upgrade`, `fuzz_ws_frame`) в CI, тестами граничных случаев RFC 6455 и нагрузочным тестом `WsWarmPool` на `10 000` сессий с проверкой отсутствия утечек файловых дескрипторов.
- **Диагностика обрывов рукопожатий в `mtevilctl status`:**
  - Для ролей `direct` и `edge` выводятся доли `client_hello_incomplete` и `inner_header_incomplete` от общего числа сессий за период аптайма с подсказкой обратиться к [ADR-005](../adr/005-wss-egress-and-turnkey-443.md).
- **Гигиена репозитория и очистка дерева развёртывания:**
  - В CI добавлен автоматический линтер `scripts/check_repo_hygiene.py`, блокирующий попадание в репозиторий реальных доменов и публичных IP вне allowlist (RFC 2606 / RFC 5737 / RFC 3849), номеров AS и названий конкретных провайдеров/хостингов.
  - Из каталога `deploy/` удалены устаревшие одноразовые операторские скрипты ранних стендовых проверок (`hour_monitor.py`, `port443_guard.py`, `window_capture.py`).
- **Маркировка `experimental`:**
  - Опции `--managed-caddy`, `--cdn` и команда `mtevilctl tuning` помечены как `[experimental]` в справке CLI, мастере и документации.

### Критическое изменение совместимости (`proxy_protocol`) и способ обхода
В `v0.4.0` допускался запуск с `"proxy_protocol": true` на не-loopback адресе (например, `0.0.0.0:24443` в сети Docker `bridge` за обратным прокси или на туннельном интерфейсе `host-network`) без ограничения IP-источника, что позволяло подменить заголовок `PROXY v2` при прямом доступе к порту. Начиная с `v0.4.1`, такая конфигурация без `proxy_protocol_allow_from` отклоняется на этапе `--check-config`.

**Как ведут себя `mtevilctl update` и `mtevilctl setup`:**
- До остановки и замены работающего контейнера утилита проверяет `config.json`. Если обнаружены `"proxy_protocol": true`, не-loopback `listen` и пустой `proxy_protocol_allow_from`, обновление безопасно останавливается с пояснением (текущий контейнер `v0.4.0` продолжает работать).
- В качестве подсказки предлагаются только частные диапазоны (RFC 1918 / RFC 6598 / IPv6 ULA) либо одиночные адреса `/32` (`/128`); публичные адреса никогда не расширяются до `/24` или `/64`, а при отсутствии подходящих интерфейсов `127.0.0.1/32` не подставляется автоматически.
- Перед записью `proxy_protocol_allow_from` автоматически сохраняется резервная копия `config.json.pre-v041-pp.bak` (права `0600`).

**Способ обхода / миграции:**
1. **Если обратный прокси (Xray / nginx stream / HAProxy) работает на том же хосте (рекомендуется):** используйте режим `--shared-443` с привязкой `listen` к `127.0.0.1:<порт>` и `network_mode: host` — в этом случае `proxy_protocol_allow_from` не требуется.
2. **Если используется Docker `bridge` + обратный прокси или туннельная подсеть (WireGuard / AmneziaWG):** укажите доверенный источник явно при обновлении:
   ```bash
   mtevilctl update --proxy-protocol-allow-from <CIDR>
   ```
   (например, `<шлюз_docker_bridge>/32` для `bridge` или частная подсеть туннеля `10.x.x.0/24` для `host-network`), либо пропишите массив `"proxy_protocol_allow_from"` в `config.json` вручную.

### Порядок обновления
1. **Одиночный узел (`direct`) и совместный порт `:443` на loopback (`--shared-443`):**
   ```bash
   mtevilctl update
   ```
2. **Каскад `edge → egress` (`split`):**
   - Сначала обновите зарубежный узел выхода (`egress`) и убедитесь в статусе `healthy`:
     ```bash
     mtevilctl update
     mtevilctl status
     ```
   - Затем обновите входной узел (`edge`):
     ```bash
     mtevilctl update
     ```
3. **Узел с `proxy_protocol: true` на не-loopback адресе (`bridge` за обратным прокси или туннельный интерфейс):**
   - Первый запуск `mtevilctl update` без флага обновит управляющий скрипт, покажет обнаруженный частный источник (при наличии) и остановится без перезапуска контейнера.
   - Повторите команду с явным разрешением источника:
     ```bash
     mtevilctl update --proxy-protocol-allow-from <CIDR>
     ```

### Откат (`mtevilctl rollback`)
Если после обновления требуется вернуться на предыдущую версию локально и без доступа к сети:
```bash
mtevilctl rollback
```
Команда восстановит сохранённый локальный образ и снимки `compose.yaml.rollback`, `.env.rollback`, `config.json.rollback`. При откате или понижении версии на релиз `< v0.4.1` поле `proxy_protocol_allow_from` автоматически удаляется из `config.json` (с сохранением копии `config.json.pre-pp-downgrade`, права `0600`), чтобы парсер `v0.4.0` с `deny_unknown_fields` запустился без ошибки. Дополнительно исходный файл до миграции доступен в `config.json.pre-v041-pp.bak`.

### Известные ограничения
- **Полевая матрица измерений H4 не проводилась:** влияние отдельных факторов фильтрации на реальных трансграничных маршрутах (порт `:443` против высоких портов, матрица размеров `ClientHello` `1200 / 1448 / 1553 / 1700`, `MSS`-клампинг, `--shared-443`) в [ADR-005](../adr/005-wss-egress-and-turnkey-443.md) зафиксировано как гипотезы до проведения полевых замеров.
- **TLS-отпечаток клиента `edge → egress` (`WSS`, H5) не изменялся и не проверялся в поле:** клиент `tokio-native-tls` на базе стокового системного OpenSSL 3.0 сохраняет стандартный серверный отпечаток JA3/JA4 без GREASE и браузерного ALPN (в [ADR-005](../adr/005-wss-egress-and-turnkey-443.md) приведён только аналитический разбор вариантов).
- **Экспериментальные функции (`--managed-caddy`, `--cdn`, `mtevilctl tuning`):** автовыпуск сертификатов ACME в sidecar-контейнере `caddy` и работа за CDN не покрыты живыми внешними E2E-тестами в офлайн-CI, а зажим `client_mss` ограничивает размер сегментов отдачи клиента (upload) на всё время TCP-сессии согласно RFC 9293.
